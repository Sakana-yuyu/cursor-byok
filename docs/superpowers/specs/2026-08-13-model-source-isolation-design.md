# 模型来源隔离设计

## 目标

让第三方 API 模型与 Cursor 账户模型在同一应用内可识别、可共存，并在凭据、请求通道、缓存、健康状态和故障切换上严格隔离。既有第三方配置不需要迁移，仍按原方式工作。

## 事实依据

- 现有本地 Agent 流由 `BidiAppend` 与 `RunSSE` 驱动；第三方模型通过 OpenAI、Anthropic、Gemini 适配器调用。
- Cursor 账号当前已能安全维护独立登录态，但只用于控制面转发。其模型执行协议尚未完成逐请求验证，不能把 OAuth Bearer 当作第三方 API Key 使用。
- cc-switch 的本机路由将真实 API Key/OAuth Token 保留在转发层，并按应用与 Provider 分隔熔断状态。

## 范围

第一阶段新增两个来源语义：

- `third_party`：默认值。使用已有 `baseURL`、`apiKey` 与协议适配器。
- `cursor_account`：只代表 Cursor 账户授权，不接收 API Key 或第三方自定义请求头；在专用账户模型网关落地前，路由必须返回明确的“不支持执行”错误。

本阶段不猜测或实现 Cursor 账户模型的请求端点，不改变 `routingMode=upstream` 的官方直连含义。

## 架构

`ModelAdapterConfig` 增加 `source` 与 `credentialScope`。规范化规则将缺失值固定为 `third_party`/`adapter_api_key`；账户源固定为 `cursor_account`/`cursor_account`，并拒绝混入 API Key、Base URL 和自定义 Headers。

解析出的渠道携带来源与凭据作用域。渠道 ID、轮询游标、健康冷却键和本地响应缓存身份都带上来源，避免相同模型名或端点在不同来源间发生碰撞。模型路由器只对同一来源的渠道做故障切换；账户源进入独立网关接口，未安装实现时立即返回可行动的错误。

前端模型编辑器明确展示来源。选择 Cursor 账户模型时不显示第三方凭据输入，并展示账号登录和“执行通道待协议验证”的状态；第三方模型保持现有编辑流程。所有发送给前端的账号状态保持脱敏。

## 失败处理与回滚

- 缺少或非法来源值按旧配置兼容规则归入 `third_party`，不会阻断已有渠道。
- `cursor_account` 在网关未实现时拒绝执行，不会降级到第三方，也不会静默切换到官方直连。
- 回滚只需删除新增来源字段，旧配置读取路径仍兼容；本次不迁移或删除持久化数据。

## 验收

1. 旧第三方配置规范化后仍可解析和路由。
2. 同模型、同端点的不同来源拥有不同身份和健康键。
3. 路由失败时不会跨来源故障切换。
4. 账户模型不会向第三方协议适配器传入 Cursor OAuth 凭据。
5. 前端能区分来源并给出账户模型当前可用状态。
